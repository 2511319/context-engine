# ТЗ-1: Фундамент `context_engine`
## Модель проектов, единый доступ к данным и честные статусы сервиса

Версия: v1  
Статус: draft (первый этап рефакторинга)  
Ответственный за архитектуру: Dushilov (product/owner), LLM-архитектор (ты+я)  
Целевая аудитория: разработчик(и) `context_engine`

## 0. Зачем это всё (контекст для разработчика)

### Глобальная задача

`context_engine` задумывался как **самообучающийся движок контекста**, который:

- индексирует код и документацию;
- строит интегрированный граф знаний (code + docs + contracts + связи);
- по запросу даёт LLM-агенту **правильный контекст**, понятный и объяснимый.

Сейчас фактическое состояние искажается:

- часть поведения зашита в ручной конфиг `engine.yml`;
- разные части кода по-разному ходят в БД;
- сервис может “как-то сработать”, даже если часть ядра мёртвая, и внешне это выглядит как «всё норм».

Результат: **зелёные тесты, но реально ненадёжный и непредсказуемый сервис**.

### Почему начинаем с этого ТЗ

Мы НЕ лезем сразу в сложный GraphRAG и policy-routing.  
Сначала нужна **здоровая основа**, которая:

1. Чётко понимает, **что такое `project`** и как с ним живут все таблицы/компоненты.
2. Имеет **один канонический слой доступа к данным** (PG и Neo4j), а не 3 разных.
3. **Честно сообщает своё состояние** (ок / down), без “тихих” фолбеков.

Если этого не сделать, любой последующий рефакторинг (граф, policy, retrieval) будет строиться на гнилых опорах.

## 1. Область действия ТЗ-1

### Что входит

1. **Модель проектов (`project`)**:
   - определение понятия `project`;
   - консистентное использование во всех слоях;
   - чистка `workspace`, `user_id` из логики.

2. **Единый Data Access Layer (DAL)**:
   - выделенный слой в `core/` для работы с Postgres и Neo4j;
   - переподключение `tools`, `api`, `mcp` на него;
   - запрет дублирующих SQL/Cypher вне DAL.

3. **Статус сервиса и отказ от фолбеков**:
   - формализация правил, когда MCP отвечает `ok`, а когда `down`;
   - убираем “магические” фолбеки (например, без графа притворяться, что всё нормально);
   - интеграция статуса в план/Explain.

4. **Минимальные изменения DevEx**:
   - убрать жёстко захардкоженные пути в скриптах;
   - намётки единого CLI (без ухода в Docker и без радикальной перестройки).

### Что НЕ входит (будет в следующих ТЗ)

- Построение полноценного **data-graph** на основе `dp_edge`, `symbols` и т.д. (ТЗ-2).
- Новая модель **policy-routing + feedback** и новый алгоритм `get_context` (ТЗ-3).
- Полноценный **Admin UI** (ТЗ-4).
- Массовое покрытие тестами и версионирование поведения (это позже, когда архитектура устаканится).

## 2. Термины и обозначения

- **Project (`project`)** — логический контекст: отдельный репозиторий/система.  
  Примеры: `context_engine`, `avia_optimizer`, `chart_genius`.

- **DAL (Data Access Layer)** — слой в `core/`, который:
  - инкапсулирует работу с Postgres и Neo4j;
  - предоставляет API в виде классов/функций;
  - единственный источник SQL/Cypher (кроме миграций).

- **MCP-сервер** — текущий `mcp/server.py`, который:
  - реализует инструмент `get_context` и другие tools;
  - общается с LLM-агентом.

- **Status** (MCP-ответ) — статус работы `get_context`:
  - `ok` — сервис выполнил контракт и отдал полнофункциональный контекст;
  - `down` — сервис не может выполнить контракт по причине серьёзной неисправности.

## 3. Требования к модели `project`

### 3.1. Причина изменений

Сейчас:

- В схемах БД есть поле `project`, местами `workspace`, `user_id`, но:
  - логика часто игнорирует это и считает, что проект один (`context_engine`);
  - части кода используют `project`, части — нет;
  - нет единой трактовки, что именно значит `project`.

Это:

- делает систему хрупкой, если добавить второй проект/репозиторий;
- усложняет анализ и отладку (данные разных проектов могут случайно перемешаться);
- мешает будущему развитию, где контекст-движок обслуживает несколько систем.

### 3.2. Целевая модель

1. **`project` — обязательно и везде**:
   - Все ключевые таблицы должны иметь `project`:
     - `code_chunks`, `doc_chunks`, `dp_datapoint`, `dp_edge`,
     - `symbols`, `symbol_refs`,
     - `dp_feedback`, `jobs`, `plans`, и т.д.
   - Все запросы к этим таблицам **обязаны фильтровать по `project`**, если только они не явно агрегируют по всем проектам (что будет редкостью).

2. **Никаких отдельных `user_id` / `workspace` в логике**:
   - Пользователь один (ты) + несколько доверенных людей.
   - Контекст и политики не должны зависеть от user-specific данных.
   - `workspace` и `user_id`:
     - либо вычищаются из кода,
     - либо остаются в схеме **только “на будущее”, но не участвуют в запросах**.

3. **MCP, API, tools работают в контексте `project`**:
   - MCP-методы (`get_context`, `ingest`, `search_raw` и т.д.):
     - принимают `project` явно (в params);
     - если `project` не указан:
       - либо используется дефолт из конфига (но это оговорено),
       - либо запрос отклоняется с понятной ошибкой.
   - HTTP API (health, plans, jobs):
     - имеют query-параметр `project`;
     - если он не указан — дефолтный проект (есть смысл сделать явный, прописанный в конфиге).

### 3.3. Конкретные задачи по `project` (порядок выполнения)

**Задача P1. Аудит использования `project`**

- Найти все места, где:
  - таблицы обращаются без фильтра по `project`;
  - `project` захардкожен (`'context_engine'`) или вычисляется странным образом.
- Составить короткий список “дыр”, где фильтра нет.

**Задача P2. Выровнять сигнатуры функций на уровне DAL (будет после создания DAL)**

- Когда DAL будет введён (см. раздел 4), все методы работы с данными:
  - принимают `project` явно;
  - внутри не делают предположений о дефолтах.

**Задача P3. MCP / API / tools: передача `project`**

- MCP:
  - `get_context`:
    - всегда принимает `project`;
    - прокидывает его дальше в DAL.
  - Остальные MCP-tools аналогично (если затрагивают БД).
- API:
  - Health/plans/jobs — добавить `project` в параметры.
- Tools:
  - `index_repo`, `memify`, `graphify` — принимать `--project` как обязательный аргумент.

**Задача P4. Очистка `workspace` / `user_id` из логики**

- Просмотреть код на наличие логики, завязанной на `workspace` и `user_id`.
- Удалить/закомментировать использование, оставив эти поля в БД только как “future reserved” (если они уже в схеме).

## 4. Единый Data Access Layer (DAL)

### 4.1. Причина изменений

Сейчас:

- В `core/` есть `PgClient`, `GraphClient` (или аналогичные),  
  но:
  - `tools/index_repo.py`, `tools/memify.py`, `tools/graphify.py` ходят в БД **напрямую** через `psycopg` и `neo4j.GraphDatabase`.
  - `api/adapters/postgres.py`, `api/adapters/neo4j.py` тоже делают свою обёртку.
- SQL/Cypher запросы к одним и тем же таблицам размазаны по репозиторию.

Это:

- создаёт риск рассинхронов — часть кода обновилась под новую схему, часть — нет;
- делает миграции и рефакторинг болезненными;
- затрудняет понимание, “как правильно” читать/писать данные.

### 4.2. Целевая модель DAL

1. **`core/` — единственный канонический слой для работы с БД**:
   - там живут:
     - `PgClient` и/или набор репозиториев (`CodeRepo`, `DocRepo`, `FeedbackRepo`, `GraphRepo`, `JobsRepo`…);
     - `GraphClient` для Neo4j.
   - все SQL/Cypher запросы (кроме миграций) сконцентрированы здесь.

2. **`tools`, `mcp`, `api` НЕ пишут SQL/Cypher сами**:
   - они вызывают методы DAL, передавая контекст (`project`, параметры).
   - любое обращение к таблицам идёт через DAL.

3. **Явное разделение ответственности**:
   - DAL не содержит бизнес-логики retrieval/graph/policy — только:
     - чтение и запись данных,
     - транзакции,
     - простые агрегации.
   - Бизнес-логика (как собирать контекст, какие веса и т.д.) — выше по слоям.

### 4.3. Структура DAL (предложение)

Файлы (пример):

- `core/dal/postgres.py`
- `core/dal/neo4j.py`
- `core/dal/repos/code_repo.py`
- `core/dal/repos/doc_repo.py`
- `core/dal/repos/graph_repo.py`
- `core/dal/repos/feedback_repo.py`
- … (расширяем по необходимости)

Примеры интерфейсов (псевдокод):

```python
# core/dal/postgres.py
class PgClient:
    def __init__(self, dsn: str): ...
    def get_conn(self): ...   # low-level, но не наружу из core
    def execute(self, sql: str, params: tuple = ()): ...
    def query(self, sql: str, params: tuple = ()) -> list[dict]: ...

# core/dal/repos/code_repo.py
class CodeRepo:
    def __init__(self, pg: PgClient): ...
    
    def upsert_code_chunk(self, project: str, chunk: CodeChunkIn) -> None: ...
    def list_code_chunks_for_project(self, project: str, limit: int = 1000) -> list[CodeChunk]: ...
    def get_code_chunks_for_paths(self, project: str, paths: list[str]) -> list[CodeChunk]: ...
    # и т.д.

# core/dal/neo4j.py
class GraphClient:
    def __init__(self, uri: str, user: str, password: str): ...
    def run(self, cypher: str, params: dict = {}) -> list[dict]: ...
````

*(Это только пример: детали можно уточнить в процессе реализации, но принцип должен быть понятен.)*

### 4.4. Конкретные задачи по DAL (порядок выполнения)

**Задача D1. Выделить PgClient/GraphClient и базовые репозитории**

* Создать (или привести в порядок, если уже есть) `PgClient` и `GraphClient`.
* Создать простые репозитории:

  * `CodeRepo` (для `code_chunks`),
  * `DocRepo` (для `doc_chunks`),
  * `GraphRepo` (минимальный набор методов для Neo4j),
  * `FeedbackRepo` (для `dp_feedback`).

**Задача D2. Переподключить MCP к DAL**

* В `mcp/server.py`:

  * убрать прямые обращения к PG/Neo4j;
  * использовать `PgClient`/`GraphClient` и репозитории.
* На этом этапе логика `get_context` **не меняется концептуально** (это будет в ТЗ-3),
  мы только заменяем низкоуровневый доступ на DAL.

**Задача D3. Переподключить API к DAL**

* В `api/adapters/postgres.py`, `api/adapters/neo4j.py`:

  * либо удалить, либо превратить в thin-обёртки вокруг `PgClient`/`GraphClient`.
* Все сервисы (`api/services/*.py`) работают через DAL.

**Задача D4. Переподключить tools к DAL**

* `tools/index_repo.py`, `tools/memify.py`, `tools/graphify.py`:

  * вместо `psycopg.connect`/`GraphDatabase.driver`:

    * инициализируют `PgClient`/`GraphClient`,
    * используют соответствующие репозитории.
* Такие скрипты становятся в основном CLI-обвязкой над функциями из `core.ingest`, `core.graph_build` и т.д.

**Важное ограничение на этом этапе**
На этапе ТЗ-1 **не меняем** бизнес-логику индексации и графа (пока).
Цель — перенести всё на DAL без изменения поведения (кроме ошибок/уголков, которые явно баги).

## 5. MCP-статусы и отказ от фолбеков

### 5.1. Причина изменений

Сейчас:

* В коде есть проверки health PG/Neo4j и фолбеки:

  * типа “если Neo4j недоступен — продолжать без графа”.
* Снаружи сервис может выглядеть “как будто работает”,
  хотя часть функциональности критически отвалилась.

Это создаёт:

* эффект “плавающих” багов (то граф есть, то его нет);
* неясность для агента/клиента: он не понимает, может ли доверять ответу;
* сложности при отладке (невозможно сразу сказать: это плохой контекст или сервис был в деградации).

### 5.2. Целевая модель статусов

* **`status="ok"`**:

  * все критичные компоненты, нужные для выполнения контракта `get_context`, доступны;
  * контекст сформирован в соответствии с архитектурой (в ТЗ-1 мы оставляем текущую логику, но без скрытых падений).
* **`status="down"`**:

  * сервис **не может** выполнить `get_context` с приемлемым качеством,
  * пример причин:

    * недоступен PG,
    * недоступен Neo4j (если он обязателен для текущей версии `get_context`),
    * внутренние критические ошибки.

**Важно:**
На этапе ТЗ-1 мы считаем, что для `get_context` **оба** компонента критичны: PG и Neo4j.

### 5.3. Изменения в `_tool_get_context`

**Задача S1. Явная проверка health в начале**

В `mcp/server.py`:

1. Перед основной логикой `get_context`:

   ```python
   if not Health.pg_ok(self.env.pg_dsn):
       return {
           "status": "down",
           "error_code": "PG_UNAVAILABLE",
           "details": { "component": "postgres", ... }
       }

   if not Health.neo4j_ok(...):
       return {
           "status": "down",
           "error_code": "GRAPH_UNAVAILABLE",
           "details": { "component": "neo4j", ... }
       }
   ```

2. Если обе проверки успешны — продолжаем строить контекст, как сейчас (с учётом того, что доступ через DAL).

**Задача S2. Удалить/отключить “тихие фолбеки”**

* Просмотреть `_tool_get_context` и связанные функции на наличие любой логики:

  * “если граф не доступен — просто не добавляем его”;
  * “если PG не доступен — вернём урезанный контекст”.
* Такие ветки **временно удалить** или превратить в явный `status="down"`.

**Задача S3. Логирование и план**

* В plan/Explain (даже в текущей минимальной схеме):

  * добавить информацию о статусе операции:

    * `status: "ok" | "down"`,
    * `error_code`, если `down`.
* Это пригодится в будущем для Admin UI и анализа.

### 5.4. Поведение других MCP-tools

На этапе ТЗ-1:

* Жёсткие требования по статусу формулируем только для `get_context`, как ключевого инструмента.
* Для других tools:

  * либо аналогично (если они зависят от тех же компонентов),
  * либо можно временно сохранить текущее поведение, но с прицелом привести их в тот же стандарт позже.

## 6. Минимальные изменения DevEx (CLI / скрипты)

**Цель:**
Сделать так, чтобы разработчик мог **устойчиво запускать** основные операции без упора в PowerShell/жёсткие пути, но **не внедрять Docker и не устраивать революцию**.

### 6.1. Причина

Сейчас:

* Есть PowerShell-скрипты с жёстко прописанными путями (`D:\project\...`);
* Старт и управление стэком завязаны на ps1;
* Это неудобно даже для автора, а для CI/других машин — почти непереносимо.

### 6.2. Целевая модель

1. Основные операции запускаются через **Python CLI** (например, `manage.py`):

   * `python manage.py ingest --project context_engine --root <path>`
   * `python manage.py build-graph --project context_engine`
   * `python manage.py health-check`

2. `.env` хранит DSN и прочие параметры окружения, а не скрипты.

3. PowerShell-скрипты:

   * либо удаляются,
   * либо превращаются в тонкие обёртки, которые просто вызывают Python CLI (и не содержат логики).

### 6.3. Конкретные задачи

**Задача C1. Создать минимальный `manage.py`/CLI**

* В корне проекта (или в `tools/cli.py`) реализовать CLI (можно на `argparse`/`click`):

  Команды (минимальный набор на этом этапе):

  * `ingest` — запускает индексатор:

    * параметры: `--project`, `--root`, возможно, `--exclude`.
  * `build-graph` — запускает `graphify`:

    * параметры: `--project`.
  * `health-check` — опционально, вызывающая текущие health-проверки.

* Внутри команды:

  * инициализируют DAL (`PgClient`, `GraphClient`);
  * вызывают соответствующие функции из `core.ingest`, `core.graph_build`.

**Задача C2. Де-факто депрекировать PowerShell-скрипты**

* Оставить их только как thin wrappers (если тебе это нужно), например:

  ```ps1
  # start_ingest.ps1
  python manage.py ingest --project context_engine --root .
  ```

* Удалить любой хардкод путей и логики из ps1.

## 7. Порядок выполнения задач ТЗ-1 (чтобы не рушить общую концепцию)

* Пока DAL нет, аккуратно трогать только локальные участки.

### Шаг 2. Ввести DAL (D1) и перевести MCP на него (D2)

  * использовал DAL.

### Шаг 3. Перевести API на DAL (D3)

### Шаг 4. Перевести tools на DAL (D4) и внедрить CLI (C1)

### Шаг 5. Жёсткие статусы MCP (S1–S3)

* В `get_context`:

  * добавить health-проверки в начале;
  * сделать `status="down"` при недоступности PG/Neo4j;

## 8. Критерии готовности ТЗ-1

### Функциональные

1. MCP `get_context`:

   * Всегда работает в контексте `project`.
   * В случае недоступности PG или Neo4j — возвращает `status="down"` и подробности.
   * При нормальной работе — `status="ok"`.

2. Любое обращение к `code_chunks`/`doc_chunks`/`dp_*`/`symbols`/`symbol_refs` идёт через DAL и учитывает `project`.

3. Tools (`index_repo`, `memify`, `graphify`) запускаются через Python CLI и используют DAL.

### Нефункциональные

1. В репозитории **нет дублирующих SQL/Cypher**, кроме:

   * DAL,
   * миграций (schemas/sql),
   * возможно, временных dev-утилит (но их надо пометить как такие).

2. PowerShell-скрипты:

   * либо удалены,
   * либо являются тривиальными обёртками вокруг CLI, без логики и хардкодов путей.

3. Код не содержит бизнес-логики, завязанной на `workspace`/`user_id`.
