# ТЗ-4: Admin UI & DevEx для `context_engine`  
## Наблюдаемость, управление и устойчивый разработческий контур

Версия: v1  
Статус: draft (четвёртый этап рефакторинга)  

Связанные документы:  
- ТЗ-1 — Фундамент: `project`-модель, DAL, статусы, отказ от фолбеков  
- ТЗ-2 — Ingest & Data-Graph: `dp_edge`, `symbols`, новый `graphify`  
- ТЗ-3 — Retrieval & Policy-Layer: data-first `get_context`, policy-routing, feedback, Explain  

Адресат: разработчик(и) `context_engine`

## 0. Контекст и глобальная задача

### Что уже должно быть к моменту ТЗ-4

Согласно предыдущим этапам:

1. **Фундамент (ТЗ-1):**
   - `project` стал обязательным контекстом во всех основных операциях.
   - Есть единый DAL (Postgres + Neo4j).
   - MCP честно возвращает `status="ok"` / `status="down"` без тихих фолбеков.

2. **Data-Graph (ТЗ-2):**
   - Ingest-пайплайн заполняет `dp_datapoint`, `code_chunks`, `doc_chunks`, `symbols`, `symbol_refs`, `dp_edge`.
   - Есть канонические URI: `file://`, `module://`, `symbol://`, `doc://`, `docsection://`.
   - `graphify` строит Neo4j-граф только из данных PG (через DAL), не опираясь на YAML.

3. **Retrieval & Policy (ТЗ-3):**
   - `get_context` разделён на data-слой и policy-слой.
   - Policy живёт в отдельном конфиге (`policy`), не переписывает реальность.
   - Feedback (pin/forget) стал частью policy.
   - Explain/plan содержит `data_route`, `policy_route`, `selection`, `plan_schema_version`.

### Зачем нужен ТЗ-4

Сейчас, даже после исправления архитектуры, есть две большие проблемы:

1. **Отсутствие полноценного Admin UI**:
   - Нельзя визуально видеть:
     - состояние сервисов (PG/Neo4j/MCP),
     - ingest/graphify-джобы,
     - планы `get_context` и влияние policy/feedback.
   - Невозможно “на глаз” понять:  
     “плохо работает потому что данные кривые, policy переусердствовал или граф не достроен”.

2. **Слабый DevEx и запуск**:
   - Исторический перекос в PowerShell-скрипты с захардкоженными путями.
   - Нет одного стабильного входа для ingest/graphify/health.
   - Сложно запускать проект на другой машине и готовить его к будущей обёртке (контейнеры/CI), даже если сейчас Docker не используется.

**Глобальная задача ТЗ-4:**

> Сделать `context_engine` не только “правильно работающим под капотом”,  
> но и **наблюдаемым и управляемым** через Admin UI,  
> а также обеспечить **устойчивый и предсказуемый DevEx** без хардкода и костылей.

## 1. Область действия ТЗ-4

### Что входит

1. **Admin UI (Next.js / существующий фронт):**
   - панель проектов;
   - health-дэшборд;
   - список ingest/graphify/jobs;
   - просмотр планов `get_context` (Explain viewer);
   - просмотр config/policy (read-only).

2. **Минимальный backend API для Admin UI:**
   - эндпоинты для health, jobs, планов, конфигов;
   - работающие поверх DAL и структур, определённых в ТЗ-1–3.

3. **DevEx & CLI:**
   - единый Python CLI (`manage.py` / `context_engine_cli.py`);
   - отказ от хардкода путей в скриптах;
   - минимальный cleanup PowerShell-скриптов (оставить только тонкие обёртки, если нужно).

### Что НЕ входит

- Полноценная визуализация графа (интерактивный graph viewer) — может появиться позже;  
  в рамках ТЗ-4 достаточно минимальной статистики по графу.
- Редактирование policy/config через UI — **сейчас только read-only**,  
  чтобы не смешивать “UI для управления” и “UI для диагностики”.
- Docker/контейнеризация/CI — на данном этапе **не реализуется**,  
  но DevEx должен быть таким, чтобы в будущем это было просто.

## 2. Основные проблемы, которые решает ТЗ-4

Чтобы разработчик понимал не только “что сделать”, но и “зачем”.

1. **Невидимость состояния системы**

   - После рефакторинга у нас сложная архитектура (data-graph, policy, feedback, DAL).
   - Без UI невозможно:
     - быстро проверить, жива ли связка PG + Neo4j + MCP;
     - понять, почему `get_context` вернул “странный” ответ;
     - увидеть, какие jobs отработали/зависли.

2. **Неявный “магический” бэкэнд**

   - Вся логика спрятана в коде, видеть её можно только через логов/консоль.
   - При изменениях config/policy есть риск:
     - не заметить, что ты кардинально поменял поведение.

3. **Тяжёлый и хрупкий запуск**

   - PowerShell с хардкодом путей делает запуск:
     - нестабильным,
     - привязанным к конкретной машине/окружению.
   - Это мешает:
     - тебе же (локально),
     - и любому человеку/CI, который захочет повторить окружение.

## 3. Целевой образ Admin UI

В этом разделе — “как должен выглядеть и ощущаться” Admin UI с точки зрения функционала.

### 3.1. Общие принципы

1. **UI — только окно в систему, не второй бэкенд**

   - Admin UI ничего не решает “за движок”:
     - не строит граф,
     - не выбирает контекст,
     - не модифицирует данные (в рамках ТЗ-4).
   - Он только:
     - читает состояние (health, jobs, планы),
     - визуализирует Explain/политику.

2. **UI ориентирован на одного power user (тебя)**

   - Не нужно думать про permission-модели, multi-user и прочее.
   - Главное — удобство и прозрачность.

3. **Мультипроектность — из коробки**

   - Везде, где возможно, UI показывает данные в контексте выбранного `project`.

---

### 3.2. Основные разделы UI

#### 3.2.1. Project selector (верхняя панель или sidebar)

**Задача:** быстро переключаться между проектами.

**Требования:**

- В шапке (или боковой панели) — селектор `project`:
  - список — либо статический (из config), либо подгружается с сервера;
  - выбранный `project` применяется ко всем страницам (health, jobs, plans…).
- Хранить выбранный `project`:
  - в состоянии приложения (React state),
  - можно дополнительно в `localStorage` (чтобы не сбрасывался при обновлении страницы).

---

#### 3.2.2. Health Dashboard

**Задача:** видеть, в каком состоянии находятся ключевые компоненты.

**Компоненты health:**

- Postgres
- Neo4j
- MCP/`get_context`
- Ingest/graphify workers (если есть отдельные процессы)
- API backend

**Требования:**

1. Страница “Health”:

   - Таблица/карточки по компонентам:
     - `name`,
     - `status` (`ok`/`down`/`degraded`),
     - последнее время проверки,
     - краткое диагностическое сообщение (если `down`).
   - Кнопка “Обновить” (refresh) для ручного ре-check.

2. Источник данных:

   - HTTP эндпоинт (например, `/api/admin/health?project=...`),  
     который собирает данные:
     - health PG и Neo4j,
     - состояние MCP (по возможности),
     - статусы внутренних сервисов.

3. Связь с MCP-статусом:

   - Если MCP `get_context` часто возвращает `status="down"`,  
     это должно быть видно (например, агрегированным счётчиком за последний час).

---

#### 3.2.3. Jobs & Ingest Dashboard

**Задача:** видеть состояние ingest/graphify/index-job’ов.

**Требования:**

1. Страница “Jobs”:

   - Таблица запущенных/прошедших job’ов:
     - `id`,
     - `type` (`ingest`, `build_graph`, возможно другие),
     - `project`,
     - `start_time`, `end_time` (если есть),
     - `status` (`pending`, `running`, `success`, `failed`),
     - `stats` (количество файлов/чанков, если хранится),
     - `error_message` (если `failed`).

2. Фильтры:

   - По:
     - `project`,
     - типу,
     - статусу,
     - диапазону дат.

3. Источник данных:

   - HTTP эндпоинт (e.g. `/api/admin/jobs?project=...&status=...`):
     - читает данные из PG через DAL (`JobsRepo`),
     - не содержит бизнес-логики, только выдаёт их в JSON.

---

#### 3.2.4. Explain / Plans Viewer

**Задача:** визуально понять, как `get_context` принимает решения.

**Требования:**

1. Страница “Plans” / “Explain”:

   - Список последних планов `get_context`:
     - `plan_id`,
     - `project`,
     - время,
     - `status` (`ok`/`down`),
     - краткий snippet запроса (обрезанный `task_text` или его хэш + summary),
     - количество избранных модулей/чанков.

   - Возможность кликнуть на план и открыть подробную карточку.

2. Детальная карточка плана:

   Отображает структуру, определённую в ТЗ-3:

   - **Общие сведения:**
     - `project`,
     - время,
     - `status`,
     - `plan_schema_version`,
     - `error_code` (если `down`).

   - **Data Route:**
     - Top-N code candidates:
       - таблица: `uri`, `module_uri`, `base_score_code`.
     - Top-N doc candidates:
       - аналогично.
     - Модули:
       - `module_uri`, `module_base_score`.
     - Графовые статистики:
       - количество нод/рёбер, разбивка по типам.

   - **Policy Route:**
     - Список `routing_rules_matched`:
       - `rule_name`, `priority`, matched_terms, основные эффекты.
     - `feedback_effects`:
       - таблица модулей/URI с `pin_bias` и `forget_penalty`.
     - `sensitive_filtered`:
       - список URI, отброшенных policy.

   - **Selection:**
     - `final_modules`:
       - `module_uri`,
       - `module_base_score`,
       - `final_module_score`.
     - `included_chunks`:
       - `uri`,
       - `type` (`code`/`doc`),
       - `module_uri` / `doc_name`,
       - `chunk_id`.

3. Источник данных:

   - HTTP эндпоинты:
     - `/api/admin/plans?project=...` — список планов;
     - `/api/admin/plans/{id}` — один план.

   - Эти эндпоинты читают данные из таблицы `plans`/`plan_log` через DAL,  
     напрямую не вызывают `get_context`.

---

#### 3.2.5. Config & Policy Viewer (read-only)

**Задача:** видеть, какие настройки движка и policy сейчас активны для проекта.

**Требования:**

1. Страница “Config / Policy”:

   - Два блока:
     - `engine` (тех.параметры),
     - `policy` (routing, sensitive и т.п.).
   - Можно показывать:
     - либо как отформатированный YAML,
     - либо как структурированный JSON/дерево.

2. Источник данных:

   - HTTP эндпоинт, например:
     - `/api/admin/config?project=...` — ассертованный агрегат:
       - `engine_config`,
       - `policy_config`.

3. **Важно:** на ТЗ-4 всё только **read-only**:

   - UI не редактирует конфиг,
   - не пишет ничего обратно в файлы/БД.

## 4. Требования к backend API для Admin UI

Чтобы разработчик не “рисовал UI в вакууме”, нужен минимальный API-контракт.

### 4.1. Общие требования

1. Все эндпоинты:

   - начинаются с `/api/admin/…` (чётко отделены от публичных API/MCP),
   - принимают `project` как query-параметр (если применимо),
   - работают через DAL, не лезут напрямую в PG/Neo4j.

2. Формат ответов — JSON.

3. Обработка ошибок:

   - для Admin UI гораздо важнее **не падать**, а отдавать:
     - `500` + JSON с `error`, `details`,  
       чем молча поглощать исключения.

### 4.2. Минимальный набор эндпоинтов

1. `GET /api/admin/health?project={project?}`

   - Ответ:

     ```json
     {
       "project": "context_engine",
       "components": [
         { "name": "postgres", "status": "ok", "message": "", "checked_at": "..." },
         { "name": "neo4j", "status": "ok", "message": "", "checked_at": "..." },
         { "name": "mcp_get_context", "status": "ok|down", "message": "...", "checked_at": "..." },
         { "name": "backend_api", "status": "ok", "message": "", "checked_at": "..." }
       ],
       "recent_down_events": [
         { "component": "mcp_get_context", "error_code": "GRAPH_UNAVAILABLE", "count": 3, "since": "..." }
       ]
     }
     ```

2. `GET /api/admin/jobs?project={project}&type={type?}&status={status?}&from={from?}&to={to?}`

   - Ответ: массив job-объектов, описанных выше.

3. `GET /api/admin/plans?project={project}&status={status?}&limit={limit?}`

   - Ответ: список кратких планов (без тяжёлых полей).

4. `GET /api/admin/plans/{id}`

   - Ответ: полный plan-объект со структурой `data_route`, `policy_route`, `selection`.

5. `GET /api/admin/config?project={project}`

   - Ответ:

     ```json
     {
       "project": "context_engine",
       "engine": { ... },   // то, как используется в core
       "policy": { ... }    // то, как используется в core.policy
     }
     ```

## 5. DevEx & CLI

### 5.1. Причина изменений

На данный момент запуск и операции:

- завязаны на PowerShell-скрипты,
- содержат хардкод путей и специфичные для машины настройки.

Это:

- делает перенос на другую машину/папку/пользователя болезненным;
- осложняет нормальное тестирование/эксперименты;
- мешает будущему движению к Docker/CI (даже если сейчас это не внедряется).

### 5.2. Целевая модель DevEx

1. **Единый Python CLI** — основной вход для всех служебных операций:

   - `python manage.py ingest --project ... --root ...`
   - `python manage.py build-graph --project ...`
   - `python manage.py health-check --project ...`
   - (при необходимости) `python manage.py run-dev-api` и т.п.

2. **`.env` — источник инфраструктурных настроек**, а не скрипты.

3. PowerShell/`.cmd`-скрипты:

   - либо удаляются,
   - либо превращаются в тонкие обёртки:
     - без логики,
     - без путей,
     - просто вызывающие Python CLI.

### 5.3. Требования к CLI

1. Файл: `manage.py` (или `tools/cli.py` с алиасом).

2. Базовые команды (минимум на ТЗ-4):

   - `ingest`:
     - параметры: `--project`, `--root`, опционально `--exclude`.
     - вызывает соответствующую функцию в `core.ingest` через DAL.
   - `build-graph`:
     - параметры: `--project`.
     - вызывает `core.graph_build.graphify` (режим apply).
   - `health-check`:
     - параметры: `--project?`.
     - вызывает те же health-функции, которые использует `/api/admin/health`.

3. Использование `argparse`/`click` — на выбор разработчика,  
   но:

   - структура команд должна быть лёгкочитаемой,
   - help (`-h`) должен быть информативным.

### 5.4. Refactor PowerShell/скриптов

1. Обнаружить все `*.ps1`/`*.cmd`/скрипты с логикой запуска.

2. Для каждого:

   - если он критически нужен тебе как “горячая кнопка” — превратить в:

     ```ps1
     # start_ingest.ps1
     python manage.py ingest --project context_engine --root .
     ```

   - удалить хардкод путей `D:\...` / `C:\...`,
   - удалить любую логику работы с БД/Neo4j — всё это уезжает в Python код.

3. Постепенно предпочитать вызов CLI напрямую (из терминала),  
   а не запуск ps1.

## 6. Ограничения и “запреты”

Чтобы не разрушить общую архитектуру:

1. **Admin UI не должен содержать бизнес-логики**:

   - никаких обращений к БД напрямую;
   - никаких попыток “по-своему” строить explain/graph;
   - UI — только клиент для backend API.

2. **Не добавлять возможность редактировать policy/config через UI в рамках ТЗ-4.**

   - Это другой класс задач (безопасность, версионирование, аудиты),
   - сейчас цель — наблюдаемость, а не редактирование.

3. **Не добавлять Docker/CI в рамках ТЗ-4.**

   - ТЗ-4 готовит почву (через DevEx), но не реализует контейнеризацию.

4. **Не вводить новые API-эндпоинты “мимо” DAL.**

   - Любые новые /api/admin/* эндпоинты работают через DAL/репозитории.

## 8. Критерии готовности ТЗ-4

### Функциональные

1. Admin UI:

   - корректно переключает `project`;
   - показывает состояние health для компонента (PG, Neo4j, MCP, backend);
   - показывает список job’ов и их статусы;
   - отображает список планов `get_context` и подробный Explain;
   - позволяет посмотреть конфиг `engine` и `policy` (read-only).

2. Backend API:

   - все `/api/admin/*`-эндпоинты работают через DAL;
   - возвращают осмысленные JSON-ответы и понятные ошибки.

3. CLI:

   - `python manage.py ingest --project X` запускает ingest;
   - `python manage.py build-graph --project X` запускает graphify;
   - `python manage.py health-check` отражает то же, что и `/api/admin/health`.

### Нефункциональные

1. В репозитории:

   - нет скриптов с хардкодом путей к локальной машине;
   - PowerShell-скрипты либо удалены, либо без логики.

2. Код UI:

   - не содержит бизнес-логики (только вызовы API и отображение данных);
