## 0. Контекст и глобальная задача (для снижения неопределённости)

### Что уже сделано на уровне архитектуры (ТЗ-1)

На этапе ТЗ-1 мы:

- выровняли фундамент:
  - **`project`** как обязательный контекст;
  - единый **DAL** для работы с Postgres и Neo4j;
  - честные статусы MCP (`ok`/`down` без “магических” фолбеков).
- **не трогали** бизнес-логику построения графа и retrieval по сути, только переподключили доступ к данным.

### Почему сейчас фокус на ingest + data-graph

Глобальная идея `context_engine` — **data-driven знание**, а не hand-made карты.  
Но в текущем коде:

- схема БД богата (`dp_datapoint`, `dp_edge`, `symbols`, `symbol_refs`),  
- а фактический граф в Neo4j:
  - частично или сильно зависит от `engine.yml`/routing;
  - **не использует** многие структуры данных по назначению;
  - не даёт честного “графа кода и документов”.

Из-за этого:

- графовый слой **обеднён**;
- Explain и визуализация основаны на частичной картине мира;
- любые последующие улучшения retrieval/policy будут работать на “кривом” фундаменте.

**Задача ТЗ-2** — сделать так, чтобы:

> **Граф в Neo4j был прямой проекцией данных индексации и анализа,  
> а не продуктом ручного YAML-routing.**

Это критический шаг перед ТЗ-3 (policy-слой + новый `get_context`).

## 1. Область действия ТЗ-2

### Что входит

1. **Канонические идентификаторы (URI) для сущностей**:
   - код: файлы, модули, символы;
   - документация: документы и секции;
   - единые правила формирования URI, используемые и в PG, и в Neo4j.

2. **Ingest-путь до data-graph**:
   - доработка `index_repo`/`memify` (если нужно) для корректного наполнения `dp_datapoint` / `code_chunks` / `doc_chunks`;
   - реализация (или доведение до ума) анализаторов:
     - code-symbol analyser → `symbols`, `symbol_refs`, часть `dp_edge`;
     - doc-link analyser → `dp_edge` для связей док ↔ код/контракты;
   - унификация и семантика `dp_edge`.

3. **Новый `graphify`**:
   - построение Neo4j-графа **исключительно** из данных PG (`dp_*`, `symbols`, `chunks`);
   - отказ от использования `engine.yml`/routing для создания узлов/рёбер.

4. **Усиление связи PG ↔ Neo4j**:
   - явный мост: любой узел графа должен быть однозначно связан с URI/ID в PG.

### Что НЕ входит (будет в следующих ТЗ)

- Изменение алгоритма `get_context` (data-слой + policy-слой) — ТЗ-3.
- Новая модель policy-routing, feedback и Explain — ТЗ-3.
- Admin UI и DevEx — ТЗ-4 (хотя реализация ТЗ-2 должна учитывать будущую визуализацию графа).

## 2. Основные проблемы, которые решает ТЗ-2

Чтобы разработчик понимал, зачем делаются изменения.

1. **`dp_edge` / `symbols` почти не используются по назначению**  
   - Схема описывает богатый граф:
     - символы кода, их определения и использования;
     - связи между кодом и документацией.
   - Фактически ingest заполняет это частично или почти никак,  
     а `graphify` мало на что опирается, кроме ручных конфигов.

2. **Граф строится не из данных, а из YAML-routing**  
   - Узлы модулей/доков и связи между ними значимо зависят от `engine.yml`.
   - Отсутствие записи в YAML может приводить к тому, что часть знаний вообще не появляется в графе.

3. **Слабая связь PG ↔ Neo4j**  
   - В PG есть `path`, `module`, `doc_name`, `chunk_id`.
   - В Neo4j есть `Module.name`, `DocSection.name` и т.п.
   - Нет чёткой, универсальной **URI-связки**, по которой можно:
     - от узла графа перейти к конкретным чанкам;
     - однозначно идентифицировать сущность в разных слоях.

Решение этих проблем — задача данного ТЗ.

## 3. Целевая архитектура ingest + data-graph

В этом разделе — картинка “как должно быть” после реализации ТЗ-2.

### 3.1. Канонические URI / ID

**Причина:**  
Без единой системы идентификаторов мы будем “склеивать” PG и Neo4j на костылях.  
URI решают это и делают архитектуру прозрачной.

#### Требование: ввести и использовать во всех слоях следующие URI-форматы

1. **Файлы кода:**

   ```text
   file://{project}/{relative_path}
````

* `relative_path` — путь от корня репозитория:

  * пример: `file://context_engine/api/services/health.py`.

2. **Модули/логические единицы кода:**

   Можно на первом этапе использовать тот же URI, что для файла, или отдельный:

   ```text
   module://{project}/{module_name}
   ```

   * `module_name` — логическое имя (например, `api.services.health` или путь без расширения).

3. **Символы (функции, классы и т.п.):**

   ```text
   symbol://{project}/{module_name}#{symbol_name}
   ```

   * пример: `symbol://context_engine/api.services.health#get_health_status`.

4. **Документы:**

   ```text
   doc://{project}/{doc_name}
   ```

   * `doc_name` — стабильный идентификатор документа (например, имя файла без `.md`).

5. **Секции документа:**

   ```text
   docsection://{project}/{doc_name}#{section_id}
   ```

   * `section_id` — устойчивый ID секции (например, slug заголовка).

**Обязательные условия:**

* Все таблицы (`code_chunks`, `doc_chunks`, `dp_datapoint`, `dp_edge`, `symbols`, `symbol_refs`) используют **эти URI** для ссылок.
* Neo4j-узлы (`Module`, `File`, `Symbol`, `DocSection` и т.п.) имеют поле `uri`, совпадающее с PG-данными.

---

### 3.2. Ingest-pipeline

Упрощённо pipeline должен выглядеть так:

1. `index_repo`:

   * перечисляет файлы репозитория;
   * пишет базовые `dp_datapoint` (тип, путь, project);
   * создаёт сырье для дальнейшего анализа (e.g. сырые записи в `code_chunks` / `doc_chunks` до чанкинга).

2. `memify`:

   * разбивает файлы на чанки (`code_chunks`, `doc_chunks`);
   * нормализует структуру;
   * добавляет `uri` (file:// / doc:// / docsection://).

3. **code-symbol analyser** (новый или доработанный):

   * читает кодовые файлы;
   * находит определения и использования символов:

     * заполняет `symbols` и `symbol_refs`;
     * создаёт `dp_edge` для связей `DEFINED_IN`, `USES` и т.п.

4. **doc-link analyser**:

   * читает документацию (Markdown/MDX/и т.п.);
   * извлекает ссылки на модули/символы/секции доков;
   * пишет `dp_edge` для связей `DESCRIBED_IN`, `MENTIONS`, `REFERENCES`.

5. `graphify`:

   * читает данные (`code_chunks`, `doc_chunks`, `symbols`, `symbol_refs`, `dp_edge`);
   * строит и обновляет Neo4j-граф:

     * создаёт узлы (File, Module, Symbol, Doc, DocSection);
     * создаёт рёбра (DEFINED_IN, DESCRIBED_IN, USES, CALLS, MENTIONS, …).

На этом этапе **`engine.yml` нигде в этом пайплайне не используется**.

---

### 3.3. Модель графа в Neo4j (целевая, на уровне ТЗ-2)

**Суть:**
Граф должен отражать:

* структуру кода,
* структуру документации,
* связи между ними.

#### Узлы (минимальный набор для ТЗ-2)

1. `(:File {project, path, uri})`
2. `(:Module {project, name, uri})`
   (возможна агрегация нескольких файлов в модуль, или модуль==файл на первом этапе)
3. `(:Symbol {project, name, module_name, uri, kind})`

   * `kind` = `function`, `class`, `method` и т.п.
4. `(:Doc {project, name, uri})`
5. `(:DocSection {project, doc_name, section_id, uri, title})`

*(Позже можно добавить `Contract` и др., но это за пределами ТЗ-2.)*

#### Рёбра (минимальный набор для ТЗ-2)

1. `(:Symbol)-[:DEFINED_IN]->(:File)`
2. `(:Symbol)-[:USES]->(:Symbol)`
   (import/вызовы/ссылки)
3. `(:File)-[:PART_OF_MODULE]->(:Module)`
   (если модуль ≠ файл)
4. `(:Module)-[:DESCRIBED_IN]->(:DocSection)`
5. `(:DocSection)-[:REFERENCES]->(:Symbol | :Module | :DocSection)`

Каждое ребро в Neo4j должно коррелировать с записью в `dp_edge` в PG.

## 4. Требования к компонентам ingest-пайплайна

Здесь — что именно требуется от каждого элемента.

### 4.1. `index_repo` / `memify` (корректировка, не полная перепись)

**Причина:**
Сами по себе они уже делают большую часть работы, но:

* URI могут не быть доведены до канонических форматов;
* `dp_datapoint` может быть заполнен частично;
* связь между `dp_datapoint` и чанками может быть не до конца выстроена.

#### Требования

1. **`index_repo`**:

   * Для каждого файла (кода или дока) создавать запись в `dp_datapoint`:

     Обязательные поля:

     * `project`,
     * `kind` (например, `code_file`, `doc_file`),
     * `uri` (file:// или doc://),
     * `path` (относительный).

2. **`memify`**:

   * Для `code_chunks`:

     * иметь поля:

       * `project`,
       * `uri` (file://),
       * `module` или `module_name`,
       * `chunk_id`,
       * текст чанка,
       * fingerprint (хэш).
   * Для `doc_chunks`:

     * `project`,
     * `uri` (doc:// или docsection://),
     * `doc_name`,
     * `section_id` (если секция),
     * `chunk_id`,
     * текст.

3. **Связь `dp_datapoint` ↔ chunks**:

   * Для каждого чанка должно быть понятно:

     * из какого `dp_datapoint` он произошёл (через `uri` и/или отдельное поле).

> **Важно:** на этом этапе не требуем крупных изменений логики чанкинга. Главное — **канонизация URI и консистентность `project`**.

---

### 4.2. Code-symbol analyser (`symbols`, `symbol_refs`, `dp_edge`)

**Причина:**
Без символов и их связей граф остаётся “по верхам” (модули/доки). Нам нужна минимальная но полезная детализация.

#### Требования

1. **Объём задачи**:

   * На ТЗ-2 не требуется идеальный парсер для всех языков.
     Достаточно:

     * поддержать основной язык(и) проекта (например, Python/TS),
     * для остальных языков можно сделать noop или простейший анализ.

2. **Таблица `symbols`**:

   * Для каждого **определения** символа (функция, класс и т.п.):

     Обязательные поля:

     * `project`,
     * `uri` (symbol://),
     * `name`,
     * `module_name`,
     * `file_uri`,
     * `kind` (тип символа).

3. **Таблица `symbol_refs`**:

   * Для каждой **ссылки/использования** символа:

     Обязательные поля:

     * `project`,
     * `symbol_uri` (на кого ссылаемся),
     * `file_uri` (откуда),
     * `context_uri` (символ/функция/метод, внутри которого используется, если возможно),
     * позиция (опционально: строка/колонка).

4. **`dp_edge` (по коду)**:

   На основе `symbols` и `symbol_refs`:

   * Создавать записи в `dp_edge` со следующей семантикой:

     Примеры:

     * `edge_kind = "DEFINED_IN"`
       `from_uri = symbol://...`, `to_uri = file://...`
     * `edge_kind = "USES"`
       `from_uri = symbol://caller`, `to_uri = symbol://callee`

   * Минимально достаточно этих двух видов; можно добавить дополнительные (например, `IMPORTS`).

---

### 4.3. Doc-link analyser (`dp_edge` по документации)

**Причина:**
Нужно связать доки и код, чтобы граф отражал, какие разделы документации описывают/упоминают какие части системы.

#### Требования

1. **Парсинг документов**:

   * Работать с форматами, реально используемыми в репо (скорее всего Markdown/MDX).
   * Для каждого документа:

     * определять `doc_name`,
     * находить секции (по заголовкам),
     * генерировать `docsection_uri` для секций.

2. **Извлечение ссылок**:

   * Выделять из текста ссылки на:

     * файлы/модули (`path`/`module_name`),
     * символы (по соглашению имени/сигнатуры),
     * другие док-секции (через `#anchor` и т.п.).

   * Разрешать их до URI:

     * `module://...` / `file://...` / `symbol://...` / `docsection://...`.

3. **`dp_edge` (по докам)**:

   Создавать записи с семантикой:

   * `edge_kind = "DESCRIBED_IN"`:

     * `from_uri = module://...` или `symbol://...`,
     * `to_uri = docsection://...`.

   * `edge_kind = "REFERENCES"`:

     * `from_uri = docsection://...`,
     * `to_uri = symbol://...` или `module://...` или `docsection://...`.

---

### 4.4. Унификация `dp_edge`

**Причина:**
Сейчас `dp_edge` — “обещанная” таблица для провенанса, но её наполнение хаотично.
Для корректного `graphify` нужно, чтобы `dp_edge` имела понятный, стабильный контракт.

#### Требования к `dp_edge`

1. Обязательные поля:

   * `project`
   * `from_uri`
   * `to_uri`
   * `edge_kind` (строка из фиксированного набора: `DEFINED_IN`, `USES`, `DESCRIBED_IN`, `REFERENCES`, …)
   * `source` (опционально: какой анализатор это создал)
   * `confidence` (опционально: оценка уверенности)

2. Набор поддерживаемых `edge_kind` на этапе ТЗ-2:

   * `DEFINED_IN`
   * `USES`
   * `DESCRIBED_IN`
   * `REFERENCES`

*(Можно добавить другие, но не обязательно для соблюдения ТЗ-2.)*

---

### 4.5. Новый `graphify`

**Причина:**
Сейчас `graphify`:

* опирается на `routing.rules` из `engine.yml`,
* создаёт узлы/рёбра на основе ручной структуры.

Нам нужно:

> граф, построенный **целиком по данным**,
> и полностью отвязанный от YAML-routing.

#### Требования

1. **Источник данных**:

   * `graphify` читает только:

     * `code_chunks` (для File/Module),
     * `doc_chunks` (для Doc/DocSection),
     * `symbols`, `symbol_refs`,
     * `dp_edge`.

   * `engine.yml` / `routing.rules` **не используются** в этом модуле.

2. **Создание узлов**:

   * Узлы создаются по URI:

     * Для всех уникальных `file://` из `code_chunks` / `dp_datapoint` → `(:File {...})`.
     * Для всех модулей (`module`/`module_name`) → `(:Module {...})`.
     * Для всех `symbol://` из `symbols` → `(:Symbol {...})`.
     * Для всех `doc://` и `docsection://` из `doc_chunks` → `(:Doc {...})` / `(:DocSection {...})`.

   * Свойства узлов:

     * минимум: `project`, `uri`, + дополнительные (name/path/doc_name/section_id/kind).

3. **Создание рёбер**:

   * На основе `dp_edge`:

     * `edge_kind="DEFINED_IN"` → `(:Symbol)-[:DEFINED_IN]->(:File)`
     * `edge_kind="USES"` → `(:Symbol)-[:USES]->(:Symbol)`
     * `edge_kind="DESCRIBED_IN"` → `(:Module | :Symbol)-[:DESCRIBED_IN]->(:DocSection)`
     * `edge_kind="REFERENCES"` → `(:DocSection)-[:REFERENCES]->(Symbol | Module | DocSection)`

   * На основе поля `module`/`file_uri`:

     * `(:File)-[:PART_OF_MODULE]->(:Module)` (если модуль ≠ файл).

4. **Режимы работы `graphify`**:

   * `dry_run`:

     * счётчики:

       * сколько узлов/рёбер было бы создано/обновлено;
       * сколько сущностей без URI/с неправильными URI;
     * без записи в Neo4j.
   * `apply`:

     * фактическое создание/обновление узлов и рёбер.

5. **Идempotентность / обновление**:

   * `graphify` должен быть безопасен для повторного запуска:

     * использовать `MERGE` / эквивалент, а не дублировать узлы/рёбра;
     * уметь обновлять свойства существующих нод (например, имя/путь).

6. **Удаление старых YAML-зависимых участков**:

   * Логика вида `merge_module_and_docs` и подобное, которая строит граф по `routing.rules`, должна быть:

     * либо удалена,
     * либо оставлена отдельно, но **не использоваться** в основном `graphify`.

## 5. Инварианты и ограничения для разработчика

Чтобы не “забегать вперёд” и не ломать глобальную концепцию:

1. **Не менять поведение `get_context` в рамках ТЗ-2.**

   * Даже если появляются новые возможности графа, алгоритм `get_context` (data- vs policy-слой) **менять нельзя** на этом этапе. Это будет в ТЗ-3.

2. **Не использовать `engine.yml`/policy для построения графа.**

   * Любые идеи “а давайте чуть-чуть подправим граф YAML-ом” — отклоняются.
     Граф на этом этапе = чистые данные.

3. **Все данные о связях должны проходить через `dp_edge` и не “обходить” его.**

   * Нельзя в `graphify` писать рёбра, которые не имеют источника в PG.

4. **URI — обязательны.**

   * Если при реализации возникнет желание “сделать временную ноду без URI” — это признак архитектурной ошибки.

Рекомендуемый порядок задач для реализации ТЗ-2.

  * обеспечить консистентность `project`.

**Выход:**
Все чанки имеют валидные URI, согласованные между PG и будущим Neo4j.

### Шаг G2. Определение и наполнение `symbols` / `symbol_refs` / `dp_edge` (по коду)

  * заполнение `symbols` и `symbol_refs`.

У нас есть таблицы символов и их связей в PG.

---

### Шаг G3. Реализация doc-link analyser и `dp_edge` (по докам)

`dp_edge` содержит связи “код ↔ доки” и “док ↔ док”.

### Шаг G4. Унификация и очистка `dp_edge`

* Пройтись по текущим данным в `dp_edge`:

  * привести формат к требуемому (project, from_uri, to_uri, edge_kind, source, confidence);
  * удалить/мигрировать старые записи в нестабильном формате.
* Зафиксировать в коде и в документации допустимые значения `edge_kind`.

**Выход:**
`dp_edge` становится структурированным и пригодным для прямого использования в `graphify`.

### Шаг G5. Новый `graphify` (dry_run)

* Реализовать новый `graphify`, который:

  * читает данные из PG через DAL;
  * строит модель узлов/рёбер в оперативной памяти;
  * в режиме `dry_run`:

    * не пишет в Neo4j,
    * выдаёт статистику и диагностирует проблемы (отсутствующие URI, неконсистентность и т.п.).

**Выход:**
Можно “сухим запуском” увидеть, что будет создано, и исправить проблемы в данных до записи в Neo4j.

### Шаг G6. Новый `graphify` (apply) и депрекация старого YAML-графа

* Реализовать режим `apply`:

  * использовать Neo4j через DAL (`GraphClient`);
  * выполнять `MERGE` нод и рёбер согласно модели.
* Отключить старые пути, завязанные на `routing.rules`:

  * либо удалить, либо чётко пометить как deprecated и неиспользуемые.
* Проверить:

  * граф строится полностью из данных,
  * `engine.yml` никак не участвует в построении.

**Выход:**
Data-graph в Neo4j отражает данные из индекса и анализаторов; YAML-routing больше не влияет на появление/исчезновение нод/рёбер.

## 7. Критерии готовности ТЗ-2

### Функциональные критерии

1. Для любого проиндексированного файла/дока:

   * есть корректный `uri` (file:// / doc:// / docsection://),
   * соответствующие чанки в `code_chunks` / `doc_chunks` содержат этот `uri`.

2. Таблицы `symbols`, `symbol_refs`, `dp_edge`:

   * заполняются для выбранного проекта;
   * используют только допустимые `edge_kind`;
   * все `from_uri` / `to_uri` валидны и соответствуют существующим сущностям (или выявляются как проблема в `dry_run`).

3. `graphify`:

   * **не читает** `engine.yml`/`routing.rules`;
   * в режиме `apply` создаёт в Neo4j:

     * `File`, `Module`, `Symbol`, `Doc`, `DocSection` с корректными `uri`;
     * рёбра `DEFINED_IN`, `USES`, `DESCRIBED_IN`, `REFERENCES`, `PART_OF_MODULE`.

4. Любой узел графа можно однозначно сопоставить с PG-хранилищем по `uri`.

### Нефункциональные критерии

1. В коде нет зависимостей `graphify` от YAML-routing (кроме, возможно, временно оставленного кода, помеченного как deprecated и неиспользуемого).

2. В документации проекта (или README для разработчика) описаны:

   * форматы URI;
   * семантика `dp_edge`;
   * базовая модель узлов и рёбер.

3. Data-graph стабильно перестраивается при повторном запуске `graphify` (идемпотентность).
