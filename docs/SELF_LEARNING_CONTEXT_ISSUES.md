# Context Engine — самонастраиваемый контекст: противоречия и возможные решения

## 1. Ожидаемая модель работы

Согласно исходному ТЗ (`context-engine-MCP_Task.md`) и rework-плану (`docs/CONTEXT_ENGINE_REWORK_PLAN.md`), контекст-движок должен:

- **Автоматически** извлекать артефакты (код/доки/подграф) по описанию задачи.
- Выдавать **детерминированный** ответ `ok/down`, но при этом использовать гибридный RAG: векторный слой (`code_chunks`, `doc_chunks`) и графовый слой (`graph subgraph`).
- Обновляться через пайплайн `index_repo -> memify -> graphify`, после чего контекст должен «самообучаться»: новое содержимое в репозитории и документах автоматически попадает в выдачу `get_context`.

## 2. Что происходит сейчас

1. **Маршрутизация жёстко завязана на `config/engine.yml`.**
   - В файле описываются **все** маршруты (`routing.rules`), и только они определяют, какие модули и документы будет видеть движок.
   - При отсутствии явного правила модуль вообще не появляется ни в Postgres, ни в Neo4j: `graphify.py` создаёт рёбра только для тех `module`, которые перечислены в конфиге.

2. **Ингест «самообучается» лишь частично.**
   - `tools/index_repo.py` действительно прогоняет весь код/доки и пишет чанки в Postgres.
   - Однако дальше `graphify.py` смотрит на `engine.yml` и вместо автоматического сопоставления использует прописанные вручную модули и docs.

3. **В результате** Neo4j показывает всего пару `DESCRIBED_IN`, даже если в `docs/external/mimic_codex` лежит множество глав: просто потому, что эти сущности не описаны в `engine.yml`.

## 3. Где логика расходится с идеей «самообучения»

| Этап | Ожидание | Текущее поведение | Противоречие |
|------|----------|-------------------|---------------|
| **Маршрутизация** | Авто-вывод модулей/доков и их связей по содержимому | Модули описываются вручную в `config/engine.yml` | Любое новое направление работы требует ручного редактирования конфига, иначе RAG слой «не видит» артефакт |
| **GraphRAG** | Graph половина отражает реальное состояние знаний | Graph содержит только то, что перечислено в `engine.yml` | Neo4j не представляет большую часть документации, контекст выдаёт минимум |
| **Playwright/интеграции** | MCP-инструменты доступны сразу | Для некоторых MCP (playwright) требуется внешний запуск, иначе в отчётах видим «unknown server» | Проверки статуса MCP не могут полагаться на автозапуск |

## 4. Основной корень проблемы

Изначальный дизайн подразумевал **управляемую маршрутизацию** через конфиг — чтобы вы точно знали, какие модули фигурируют в ответе. Это полезно, но в текущей постановке **рушит идею самонастраивающегося контекста**: граф не растёт автоматически, и любой новый документ игнорируется, если нет соответствующего правила.

## 5. Варианты выхода

### Вариант A. Генерация конфигурации

1. Дополнить `tools/index_repo.py` сбором структуры проекта (папки, namespace, сервисы).
2. На основе этой структуры автоматически формировать блок `routing.rules` (либо отдельный YAML, который потом сливается в `engine.yml`).
3. После каждого `index_repo` мы получаем обновлённый список модулей/доков — «самообучение» сохраняется, конфиг остаётся источником истины.

**Плюсы:** минимальные изменения в MCP-слое; сохраняется детерминизм.  
**Минусы:** надо написать генератор правил, следить за коллизиями, возможны ложные срабатывания.

### Вариант B. Убрать жесткую зависимость от `engine.yml`

1. Оставить `engine.yml` только для базовых настроек (веса, лимиты) и overrides.
2. В `graphify.py` автоматически создавать `Module` из данных Postgres (например, по `module` в чанке или по пути файла).
3. Документы привязывать по эвристике (rel`DESCRIBED_IN` к модулям, если `doc_name`/секции упоминают модуль).

**Плюсы:** минимальный ручной труд, граф строится из фактического содержимого.  
**Минусы:** нужно продумать эвристику, чтобы связки были разумными; детерминизм может страдать.

### Вариант C. Комбинированный подход

1. `engine.yml` хранит базовые правила + overrides.
2. Ingest создаёт список новых модулей/сущностей автоматически, но сверяется с доп. white/blacklists.
3. Graph хранит как «официальные» сущности, так и автоматически найденные (с пометкой confidence).

**Плюсы:** сочетает контроль и автоматизацию.  
**Минусы:** сложнее реализация, потребуется доп. UI для фильтрации связей.

## 6. Инвазивность изменений

| Компонент | Файлы | Риск / объём работ |
|-----------|-------|--------------------|
| **index_repo/memify/graphify** | `tools/index_repo.py`, `tools/graphify.py`, возможно `core` | Придётся переписать часть логики, чтобы генерировать/поддерживать модульный граф автоматически. Затронет основные пайплайны, но изменение локализовано. |
| **mcp/server.py** | `mcp/server.py` | Если меняем источники данных (например, добавляем новые таблицы), придётся адаптировать `get_context` / логирование. |
| **ui/api** | `api/services/*.py`, `ui/src/pages` | Минимально: UI уже умеет показывать обновлённые данные, главное — чтобы бекенд отдавал новые метрики. |

В сумме — изменения средние по инвазивности: придётся модифицировать инструменты ingest и в меньшей степени `mcp/server.py`, но архитектура не рушится. Однако пока `engine.yml` остаётся узким горлышком, приложение не выполняет свою ключевую цель («самообучающийся контекст»), что делает текущий функционал почти бессмысленным.

## 7. Рекомендации

1. **Зафиксировать требование**: система должна автоматически строить модульно-документные связи.  
2. **Выбрать вариант** (A/B/C) и запланировать разработку. Если важна управляемость — генерация конфига (A). Если важна гибкость — автоматизация на уровне graphify (B или C).  
3. **Устранить проблемы с MCP-серверами**: поднять Playwright-MCP, зарегистрировать context_engine в окружении, чтобы health-checkи проходили.

---

> Пока `engine.yml` перечисляет лишь несколько маршрутов, RAG/GraphRAG стэк работает только на эти модули и не «учится» на остальной кодовой базе. Без пересмотра логики ingest мы получаем сильно урезанную версию изначальной идеи.
